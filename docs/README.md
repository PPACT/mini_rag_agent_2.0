# docs/ 说明

## 文档放置规则

> **与 RAG 业务无关的开发文档，一律放 `docs/`，不要散落在项目根目录。**

**例外**（功能性要求，必须留根目录）：

| 文件 | 为什么必须在根目录 |
|---|---|
| `CLAUDE.md` | Claude Code 只从项目根加载此约定，移走即失效 |
| `README.md` | 仓库门面，约定俗成 |

> 这条规则是为了修一个真实发生过的问题：开发文档曾散落在根目录（计划、规划、回顾各一处）。
> 根因是**隐式约定会被侵蚀**——所以写下来，而不是靠记忆。

---

## 这个目录是什么

**项目开发文档**——给人看的：方案、记录。与系统的运行时行为**完全无关**。

## 这个目录不是什么（**边界**）

⚠️ **不是 RAG 知识库的原始文本。** `docs/` 里的任何内容都不会被 RAG 系统读取、解析或向量化。

对 RAG 项目来说 `docs` 这个名字确实容易误读，特此明确边界：

| 内容 | 位置 | 性质 |
|---|---|---|
| **项目开发文档** | `docs/`（本目录） | 给人看的，与运行无关 |
| **RAG 知识库文本**（用户上传的） | `data/uploads/` | 业务数据，gitignore |
| **RAG 测试语料**（评测夹具） | `eval/corpus/`、`eval/corpus_synth/` | 测试用，与线上知识库无关 |
| **接口文档** | 运行时 `/docs`（FastAPI 自动生成） | OpenAPI，非本目录 |

---

## 文档地图

> **维护约定**：每份文档都声明**自己的权威范围**；同一事实只保留**一个**来源。
>
> **三份公开文档之间的裁决规则**：
> **看「系统现在长什么样」→ `架构方案.md`**；
> **看「当时为什么这么选、踩过什么坑」→ `开发记录.md`**；
> **看「文档放在哪、边界在哪」→ 本文件**。
>
> 历史教训：本目录曾同时存在多份互不标注时效的「现状描述」，读者无法判断该信哪份。
> **因此每份文档都必须写清"我负责回答什么、我不负责什么"。**

| 文件 | 权威范围（只答这一个问题） |
|---|---|
| `README.md` | **本说明**：文档放在哪、边界在哪、谁是权威 |
| `架构方案.md` | **系统现在长什么样**：定位 / 选型 / 分层 / 数据模型 / 真实链路 / 扩展点 / 已知边界 |
| `开发记录.md` | **当时为什么这么选、踩过什么坑**：搭建过程、关键设计决策、编码结论、立项期评估存档 |

> 新增文档前先问：**能不能并进上面三份之一**？能 ⇒ 不新增；不能 ⇒ 才新建，并在本表登记权威范围。
